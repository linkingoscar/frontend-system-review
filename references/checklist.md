# 工程与架构评审清单

仅选择与项目范围相关的条目。先确认事实，再形成发现；“没有采用某工具”本身不是问题。

## 1. 业务与约束

- 识别核心用户、关键任务、业务风险、流量形态和发布频率。
- 判断 SEO、登录态、实时性、离线、多租户、国际化、合规和浏览器支持要求。
- 检查渲染、缓存和数据一致性方案是否匹配页面类型，而不是全站一刀切。
- 判断架构复杂度是否匹配团队规模、技能、招聘和维护成本。
- 确认成功指标、性能预算或服务目标是否存在，并能关联到用户或业务结果。
- 区分当前痛点、预期增长问题和纯理论风险。

## 2. 依赖与构建

- 检查 `package.json`、lockfile、包管理器和运行时版本是否一致且可复现。
- 检查 scripts 是否覆盖开发、typecheck、lint、test、build 和必要的生成步骤。
- 检查框架、构建器和核心依赖是否处于可维护范围；不要只因非最新版就报问题。
- 搜索职责重复或互相冲突的请求库、状态库、日期库、UI 库和 CSS 方案。
- 检查直接依赖与实际 import 是否匹配，避免幽灵依赖和错误的 peer dependency。
- 检查环境变量的命名、客户端暴露边界、schema 校验和构建时/运行时语义。
- 检查产物是否确定、可追踪且不会把测试数据、source secret 或本地路径打包进去。
- Monorepo 中检查 workspace 边界、任务依赖、缓存输入、affected 策略和共享配置版本。
- 只在有规模证据时建议远程缓存、复杂任务编排或拆包。

## 3. 架构与模块边界

- 从目录、import 图和公共 API 判断业务边界是否可见。
- 检查页面、feature/domain、共享组件、基础设施和跨切面代码是否职责清晰。
- 检查业务逻辑是否全部堆在组件、hooks、store 或单个 service 中。
- 检查模块能否通过稳定入口导入，是否存在深层导入、循环依赖和反向依赖。
- 检查共享层是否成为无所有者的杂物间；确认共享抽象至少有两个真实消费者。
- 检查边界是否有 lint、dependency rule、package export 或测试约束，而非只靠约定。
- 检查错误、日志、配置、权限、国际化和数据访问等横切能力是否一致。
- 评估可替换性：框架 API 是否泄漏到领域逻辑，第三方服务是否有清晰适配边界。
- 对微前端检查独立发布需求、运行时隔离、共享依赖、路由、样式和故障边界；没有组织级必要性时优先更简单的模块化。

## 4. 类型、API 与数据正确性

- 检查 TypeScript 严格度及逃生口：`any`、非空断言、类型断言、`@ts-ignore`。
- 区分编译期类型与运行时不可信数据；检查 API、环境变量、URL 参数、存储和消息边界的验证。
- 检查 API 契约是否生成、共享或有一致的变更流程，避免客户端与服务端手写漂移。
- 检查错误响应、分页、金额、时间、时区、枚举、nullable 与缺失字段语义。
- 检查 schema 验证失败后的错误处理、遥测和用户恢复路径。
- 检查表单规则是否与服务端约束一致，并防止重复提交、竞态和过期响应覆盖新状态。
- 对交易或副作用操作检查幂等、重试边界、乐观更新回滚和一致性。
- 检查数据规范化与视图模型，避免 API 形状无控制地扩散到整个 UI。

## 5. 状态、路由与渲染

- 区分 server state、URL state、form state、local UI state 和跨会话持久状态。
- 检查缓存 key、失效、stale 策略、错误重试、取消、去重和预取是否一致。
- 检查全局 store 是否保存可由 URL、查询缓存或局部组件拥有的数据。
- 检查 effect 是否用于真正的外部同步，而不是派生状态或普通事件逻辑。
- 检查 loading、empty、partial、error、offline、retry 和 success 状态是否完整。
- 检查路由参数、search params、权限、not-found、error boundary 和返回导航行为。
- 检查 SSR/SSG/ISR/CSR/server component/island 的选择是否匹配可索引性、个性化和交互成本。
- 检查 hydration 一致性、浏览器 API 守卫、客户端边界和序列化成本。
- 检查认证与授权：前端只能改善体验，服务端必须执行真实授权。
- 检查长列表、复杂表格、图表和实时数据的容量上限与退化策略。

## 6. 组件与设计系统工程

- 区分 primitive、复合组件、业务组件和页面组合；避免万能组件与布尔参数爆炸。
- 检查组件 API 是否以意图和组合为中心，避免暴露内部 DOM 或样式实现。
- 检查 design token 是否覆盖颜色、排版、间距、圆角、阴影、层级和动效，并能表达语义。
- 检查组件所有状态：hover、focus-visible、active、disabled、loading、error、empty、success。
- 检查语义 HTML、键盘行为、焦点管理和可访问名称是否内建在基础组件。
- 检查 responsive、国际化长文本、RTL、缩放和暗色模式是否在组件层有策略。
- 检查 Storybook 或等价文档、视觉回归、版本策略、变更说明和使用边界。
- 判断抽象是否降低重复与错误；只有单一场景时优先局部清晰实现。

## 7. 测试与质量门禁

- 从关键风险反推测试，而不是先看覆盖率百分比。
- 检查领域规则、schema、状态机和纯逻辑是否有快速稳定的单元测试。
- 检查组件测试是否验证用户可见行为、语义和交互，而非内部实现。
- 检查 API mock 是否集中、贴近契约，并能覆盖错误、延迟和边界响应。
- 检查核心任务是否有端到端测试，并覆盖认证、交易、权限或恢复路径。
- 检查测试是否会在 CI 中真实执行，是否存在大量 skip、重试掩盖或 flaky 基线。
- 检查时间、网络、随机数、并发和外部服务是否可控。
- 检查视觉回归和 a11y 自动检查是否放在最有收益的组件与路由，而不是盲目全量。
- 检查失败信息、fixture、factory 和测试环境是否便于定位与维护。

## 8. CI/CD 与发布

- 检查安装、缓存、lint、typecheck、test、build、E2E 和安全检查的依赖关系。
- 检查 CI 是否使用冻结 lockfile、明确运行时版本和生产等价构建。
- 检查分支保护是否能阻止失败或跳过的关键门禁进入主线。
- 检查构建产物、commit、source map、release 和部署环境能否互相追踪。
- 检查 preview、staging、canary、Feature Flag 或其他降低爆炸半径的机制是否匹配风险。
- 检查数据库或后端契约变更与前端发布的兼容窗口。
- 检查回滚或前滚方案是否可操作、被演练且不依赖单个人。
- 检查部署失败、健康检查、告警和发布后验证是否闭环。
- 对构建速度问题先量化关键路径，再建议缓存、并行或任务拆分。

## 9. 安全、隐私与供应链

- 搜索硬编码 secret、私钥、token、内部 URL、source map 敏感内容和公开环境变量。
- 检查不可信 HTML、URL、Markdown、富文本和模板渲染的 XSS 边界。
- 检查认证 token 存储、Cookie 属性、CSRF、CORS 和跨窗口消息验证。
- 检查开放重定向、文件上传/下载、iframe、第三方脚本和动态代码执行。
- 检查权限与租户隔离是否在可信服务端执行。
- 检查 CSP、安全响应头和依赖安全；根据部署环境区分前端可控与平台可控项。
- 检查日志、分析、录屏、错误监控和 URL 中的个人或敏感数据。
- 检查同意管理、数据保留、删除和地区合规是否与业务要求匹配。
- 检查依赖来源、生命周期脚本、锁文件完整性、更新流程和高风险 abandoned package。
- 不根据版本号单独认定漏洞；需要公告、可达调用路径和影响版本证据。

## 10. 可观测性与运维

- 检查前端错误、unhandled rejection、资源失败和 API 失败是否可见。
- 检查 source map 是否私密上传并与 release 对齐。
- 检查日志、trace、request ID 和后端事件是否能串起关键任务。
- 检查真实用户性能、设备、地区、网络和版本维度是否可分析。
- 检查告警是否关联用户影响与服务目标，避免只监控错误数量。
- 检查敏感字段脱敏、采样、保留期限和监控工具失效路径。
- 检查 Feature Flag、实验和发布版本是否进入事件与错误上下文。
- 检查事故后能否回答“谁受影响、从何时开始、哪个版本、如何恢复”。

## 11. 场景化增补

### 营销与内容站

- 加重 SEO、可索引 HTML、metadata、canonical、sitemap、结构化数据、LCP、字体、图片和 CMS 预览。
- 检查第三方营销脚本、同意管理、实验和转化追踪的业务价值与性能成本。

### 电商与交易

- 加重价格与库存一致性、搜索、购物车、幂等、支付恢复、重复提交、监控和审计。
- 检查缓存不会显示错误价格或越权数据，发布可快速止损。

### SaaS 与后台

- 加重权限、多租户、URL 状态、复杂表单、表格、批量操作、实时性和错误恢复。
- 检查数据密度、键盘效率和长时间会话中的过期状态。

### 内部工具

- 加重开发效率、稳定性、权限与审计；降低对营销 SEO 和重型平台化的要求。
- 不因用户少而忽略会造成错误业务操作的数据正确性。

### 多团队平台或 Monorepo

- 加重所有权、依赖方向、发布边界、兼容策略、共享配置、变更传播和模板治理。
- 检查平台规范是否有自动约束与迁移路径，而不是只写文档。

### 组件库或设计系统

- 加重语义 token、可访问性、组合 API、文档、视觉回归、版本兼容和消费方升级成本。
- 检查基础组件是否强制正确默认值，同时保留必要的扩展点。

## 12. 常见红旗与反证

以下只能作为搜索线索，不能自动升级为 finding：

- 无 lockfile、非 strict TypeScript、多个状态库、巨型组件、全局 store、`useEffect` 请求、无 E2E、无监控、无灰度、bundle 偏大。
- 使用微前端、Monorepo、Redux、CSS-in-JS 或特定框架。
- 依赖不是最新版、覆盖率低、目录不是某种标准结构。

形成发现前回答：它是否可达、是否造成真实后果、是否超出本次变更、是否存在合理上下文、是否有更小修复。
