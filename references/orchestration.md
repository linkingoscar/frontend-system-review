# 并行评审与独立验证

只在任务可明确拆成独立证据面、且运行环境支持子代理时使用。并行不是质量证明；独立反证、统一证据门和根因去重才产生价值。

## 1. 何时使用

适合并行：

- 深度审计同时覆盖架构、运行时、a11y、性能或发布链；
- Monorepo、多应用或多个代表性路由可以按边界拆分；
- 候选 P0/P1 需要独立复现或反证；
- 正式上线门禁需要降低单一审查者确认偏差。

不要并行：

- 单文件、小 diff 或快速扫描；
- 子任务依赖同一未稳定结论；
- 多个代理只会重复读取同一批文件；
- 运行会触碰生产、真实数据或需额外授权。

根据独立证据面的数量决定代理数，不按仓库体积机械扩容。通常 2–4 个专职角色已经足够。

## 2. 推荐角色

按任务选择，不要求全部启用：

| 角色 | 输入 | 只交付什么 |
|---|---|---|
| 范围与架构 | 仓库、change-scope、业务约束 | 项目画像、调用链、候选 finding JSON |
| 运行时与体验 | URL、路由矩阵、允许的认证状态 | 截图、交互步骤、runtime artifact、候选 finding JSON |
| 专项检查 | 明确的 a11y、性能、安全或发布范围 | 专项证据与局限，不做全局总分 |
| 独立验证者 | 当前报告、原始仓库和 artifact | 对每条发现的 confirmed / weakened / rejected 与理由 |

根代理始终负责范围、严重度校准、跨域冲突、去重、最终结论和用户沟通，不把这些责任平均分散。

## 3. 上下文隔离

给调查代理传目标、原始材料、skill 路径和权限边界，不传预期答案。给独立验证者传当前报告和可复查原始证据，但不要传作者的推理过程、修复偏好或“应该通过”的结论。

验证提示应要求：

1. 精确复查引用和 artifact；
2. 尝试寻找使 finding 不成立的调用条件、框架行为或业务约束；
3. 对运行态问题按原步骤复现；
4. 判断严重度与影响是否被证据支持；
5. 返回结构化状态，不直接重写最终报告。

同一代理不要同时担任某条 finding 的作者和唯一验证者。

## 4. 证据交接

调查代理交付：

- 自己检查的明确范围和未覆盖项；
- 仅包含可报告候选的 JSON 片段；
- 相对仓库的 source 路径与当前行号/quote；
- 相对 artifact root 的工具日志、截图或 trace；
- 实际执行的命令、退出码、环境版本和脱敏说明；
- 未达 finding 门槛的风险单独列出。

代理间不要以自然语言“我确认有问题”代替原始证据。临时 ID 可重复，根代理合并时重新编号并计算稳定 fingerprint。

## 5. 根代理合并

按以下顺序合并：

1. 运行 `verify_findings.py --strict` 排除失效证据；
2. 按根因合并跨文件或跨路由症状；
3. 正式门禁覆盖全部 P0/P1 与严格校验产生语义可达性警告的 finding；比较验证者结论，删除 rejected，降低 weakened 的置信度或移入未验证风险；
4. 检查同一修复是否会引入其他专项风险；
5. 统一 P0/P1/P2、成本、验证步骤和上线结论；
6. 使用基线差异、门禁和评审包命令生成最终事实源。

如果两个证据充分的专项结论冲突，保留冲突及决策条件，不用投票代替技术判断。

## 6. 失败与停止条件

- 代理输出没有原始证据：退回补证，不进入 findings。
- 运行环境不同导致复现结果冲突：记录双方环境并在同一环境复测。
- 认证状态或数据不安全复制：停止该运行态分支，改列未验证风险。
- 独立验证连续拒绝同一模式：修订规则或 workflow，不靠换代理“刷通过”。
- 新证据不再改变最高风险、结论或修复顺序：停止扩张范围，交付剩余风险。
