# Frontend Architecture Review

以业务约束和可验证证据判断架构是否降低真实风险。不要把目录整齐、依赖流行或模式数量当作成熟度。

## 边界

先记录产品类型、团队规模、部署模型、目标用户、关键任务、合规与演进约束。范围不清时采用最小合理范围并标出推断。

仅在用户明确要求时修改代码。评审默认只读；命令结果、文件、行号和依赖关系不得编造。

## 评审顺序

1. 盘点入口、构建、工作区、框架、包管理、锁文件、生成物与部署单元。
2. 从关键用户任务反向追踪路由、数据获取、状态、权限、错误处理和恢复路径。
3. 检查模块所有权、依赖方向、循环、跨层调用、公共层膨胀和变更扩散。
4. 检查服务端/客户端边界、缓存所有权、并发、竞态、失效与一致性。
5. 检查类型、API、事件、配置和持久化契约是否有运行时校验、兼容策略和失败语义。
6. 检查组件与设计 token 是否服务复用和一致性，而非制造抽象税。
7. 检查测试金字塔是否覆盖边界与高风险流程，构建和发布是否可追踪、可回滚。
8. 检查秘密、权限、第三方脚本、供应链与可观测性边界。

## 判断纪律

- 先证明依赖方向和运行路径，再建议拆包、Monorepo、微前端、状态库或重写。
- 将“当前缺陷”“容量临界点”“未来演进风险”分开，不能用未来假设升级当前严重度。
- 对每个候选问题寻找反证：现有约束、测试、边界或发布机制是否已经降低风险。
- 性能、可访问性和视觉问题若依赖运行事实，交给对应专项复现，不从源码直接下结论。

## 输出

每条 finding 包含稳定指纹、P0/P1/P2、置信度、证据、业务/用户影响、根因、最小修复和验证步骤。另给出：架构画像、关键依赖图的文字描述、最高杠杆的 30/60/90 天演进顺序、已检查与未覆盖范围。

被总控调用时只返回候选 findings 和专项覆盖说明，不单独宣布最终上线结论。
