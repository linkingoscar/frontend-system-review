1. 证据状态

## 1. 证据状态

给每条发现标记一种状态：

| 状态 | 含义 | 写法 |
|---|---|---|
| 已确认 | 有可复现运行时结果、工具输出或精确源码证据 | 作为正式 finding |
| 高可能 | 多处静态证据支持，但缺少运行时或业务条件确认 | 写明假设和验证步骤 |
| 待验证 | 影响可能较高，但当前材料不能证明 | 放入“未验证风险”，不直接判 P0 |
| 不适用 | 与项目画像无关 | 从评分分母移除 |

置信度与严重度互不替代：

- **高置信度**：能复现，或证据直接且上下文完整。
- **中置信度**：代码路径可信，但仍依赖环境、数据或调用条件。
- **低置信度**：主要来自间接线索或缺失材料；通常不要作为正式 finding。

## 2. 严重度

按实际后果而非规则名称分级。

### P0 — 阻断

仅用于已确认或极高置信度、需要在发布或合并前解决的问题，例如：

- 可利用的高影响安全或隐私问题；
- 数据损坏、越权、交易错误或核心任务不可完成；
- 构建/发布失败，或高风险发布没有可行恢复路径；
- 关键用户群完全无法操作核心任务；
- 明确且严重的生产性能或稳定性退化。

“没有测试”“没有监控”“没有 runtime schema”通常不能单独构成 P0，除非能证明它直接使当前发布不可接受。

### P1 — 重要

用于明显损害用户、业务、可靠性或持续交付，且应进入近期计划的问题，例如：

- 核心流程容易回归或错误恢复不完整；
- 可访问性显著退化但仍有绕行方式；
- 架构边界、状态或契约造成持续错误与高维护成本；
- 关键页面性能、响应式或 SEO 明显不达业务目标；
- CI、发布、监控存在实质性盲区。

### P2 — 改进

用于影响有限、可延后或主要提升一致性、效率和打磨的问题。纯偏好不要伪装成 P2。

## 3. Finding 质量门

每条正式 finding 必须回答：

1. 在哪里或如何复现？
2. 实际观察到了什么？
3. 谁会受到什么影响？
4. 为什么当前行为不是合理设计？
5. 最小可行修复是什么？
6. 如何证明修复有效且没有回归？

缺少 1–3 时优先继续调查；仍无法确认时降为待验证事项。

## 4. 可选评分模型

仅在用户要求量化或正式体检时使用。每个适用维度评 0–5 分：

| 分数 | 含义 |
|---:|---|
| 0 | 能力缺失且已造成严重风险 |
| 1 | 多个阻断或系统性缺陷 |
| 2 | 明显不足，依赖人工补偿 |
| 3 | 基本可用，存在清晰改进项 |
| 4 | 良好，有可靠实践与少量缺口 |
| 5 | 成熟、可验证且持续治理 |

维度与默认权重：

| 维度 | 权重 |
|---|---:|
| 业务与架构匹配 | 8 |
| 技术栈、依赖与构建 | 8 |
| 模块边界与可维护性 | 10 |
| 类型、API 与数据正确性 | 10 |
| 状态、路由与渲染 | 8 |
| 性能与 SEO | 10 |
| UI、响应式与设计系统 | 8 |
| 可访问性 | 8 |
| 测试体系 | 8 |
| CI/CD 与发布恢复 | 10 |
| 安全、隐私与供应链 | 8 |
| 可观测性与运维 | 4 |

总权重为 100。若维度不适用，标为 `N/A` 并按剩余适用权重归一化：

```text
总分 = Σ(适用维度权重 × 维度分数 / 5) / Σ(适用维度权重) × 100
```

证据覆盖率：

```text
证据覆盖率 = Σ(已有足够证据的适用维度权重) / Σ(适用维度权重) × 100%
```

覆盖率低于 70% 时，将总分标为“暂定”；不要用未检查项补默认分。

可使用以下说明性等级：

| 总分 | 等级 | 含义 |
|---:|---|---|
| 85–100 | A | 成熟，风险受到持续治理 |
| 70–84 | B | 可用且总体稳健，有明确改进项 |
| 55–69 | C | 存在结构性风险，需要专项治理 |
| 0–54 | D | 多个关键能力不足，不宜仅做局部打磨 |

评分不能抵消发现：任何已确认 P0 都优先于总分。

## 5. 上线或合并结论

独立于分数给出一个结论：

- **阻断上线/合并**：存在已确认 P0。
- **修复后可上线/合并**：无 P0，但一个或多个 P1 与本次目标直接相关。
- **可上线/合并但需跟进**：无阻断问题，剩余风险有明确 owner 和时限。
- **可接受**：未发现影响目标的可报告问题；仍需说明未覆盖范围。
- **无法判断**：关键材料或运行时条件缺失，任何结论都会误导。

不要把“无法判断”写成“失败”，也不要因没有发现就宣称绝对安全。

## 6. 基线与门禁

基线必须是某次已复核、已接受且保留完整 findings 的 `review.json`。用稳定 fingerprint 比较逻辑问题，不用 F-编号、当前行号或报告顺序匹配。

- `new`：当前存在、基线不存在；
- `resolved`：基线存在、当前不存在；
- `changed`：同一问题的严重度、状态、影响或修复发生变化；
- `regression`：严重度升高，或状态/置信度变得更确定；
- `unchanged`：关键语义未变。

增量门禁可以只阻止新增或回归，但当前报告仍应呈现全部存量问题。不要用基线把未修风险包装成通过。

默认门禁自动阻止 `block`、`ready_after_fixes`、`unable_to_determine` 结论和已确认 P0，避免“修复后才可上线”却显示通过。更细的 finding 数量、评分、证据覆盖率或未验证风险门槛必须由团队基于历史样本校准，并明确 owner、例外批准和到期复查。门禁失败表示政策条件未满足，不等同于工具执行失败；输入或环境错误使用独立退出码。
